# Aho–Corasick の実装解説

[使用法に戻る](../aho_corasick.md) / [実装](https://github.com/sen469/kyopro-library/blob/main/lib/kyopro/aho_corasick.hpp)

## 目的と基本原理

複数のパターンをTrieに登録し、テキストを1回読むだけで同時に検索します。
状態は「読み込んだ文字列の接尾辞のうち、Trieに存在する最長の接頭辞」です。
例えば `he` と `she` を登録して `she` を読むと、現在の状態は `she` ですが、その接尾辞 `he` も同時に一致します。

## 内部データ

各ノードはTrieの実際の子 `child`、各文字での完成した遷移表 `go`、そのノードで終わる登録ID `ids`、
`failure`、`output_link`、接尾辞も含む一致数 `match_count` を持ちます。
`terminal_` と `length_` は各IDの終端・パターン長、`order_` は根からの幅優先順です。

実際の子と遷移表を別に持つことで、構築後の追加登録をTrieの辺と混同せずに扱えます。
同じパターンの登録は終端ノードを共有し、IDだけを別々に保存します。空文字列のIDは根に保存します。

## failure linkと遷移表

`failure[v]` はvの表す文字列の真の接尾辞のうち、Trieにある最長のものです。根のfailureは根自身です。
深さ1のノードのfailureは根、それ以外の子uについては、親vのfailureから同じ文字を読む遷移先になります。

幅優先で構築すると、参照するfailure側の遷移表はすでに完成しています。
実際の子がある文字はその子へ、ない文字はfailure側の遷移へ進めます。根に子がない文字は根へ戻ります。
これにより `next` はfailureを毎回たどらず、配列アクセスで遷移できます。

`build` は実際の辺だけを使って全ノードを処理し直します。
パターンの追加で既存ノードのfailureが変わる場合や、空文字列・重複パターンを追加した場合にも対応します。
ノード番号・登録IDは変えません。

## 一致の個数と列挙

各ノードの一致数は `ids.size() + failure先のmatch_count` です。
根では根自身のID数を使います。`count_matches` は先頭境界の根の一致数と各文字を読んだ後の一致数を加えます。

`output_link` はfailure側にある最も近い終端ノードを指します。
そこにも終端がなければさらに先のoutput linkを使い、存在しない場合は-1です。根自身のoutput linkは-1にします。
`match_ids` と `find_all` は現在のノードとoutput link上のIDを列挙します。
リンクを進むたびに少なくとも1件の一致を出力するため、列挙時間を一致数に比例させられます。

接尾辞の全IDを各ノードにコピーしないことが重要です。
`a`, `aa`, `aaa`, ... のような登録で一致情報の重複保存が膨らむことを防ぎます。
リンクは短い接尾辞へ向かうので、列挙順は長さの降順です。同じ終端のIDは登録順です。

## パターンごとの出現回数

`count` はテキストを読み、各状態を訪れた回数を数えます。
ある状態に到達すれば、そのfailure上のパターンも一致するため、幅優先順の逆順で
`visits[failure[v]] += visits[v]` を行います。根から根への伝播は行いません。
各パターンの答えは、その終端ノードに集まった訪問回数です。

最初に `visits[0] = 1` として、文字を読む前の境界も数えます。
他の境界はテキスト走査の訪問から根へ集まるので、空文字列の回数はテキスト長+1になります。
一致を列挙しないため、答えの合計が大きくても走査・伝播の時間は増えません。

## 計算量の根拠

文字種数をσ、ノード数をV、登録数をP、テキスト長をNとします。
各ノードの2つの配列がσ要素で、IDは各登録につき1個なので空間は $O(V\sigma+P)$ です。
構築は各ノード・各文字を1回処理するため $O(V\sigma)$、再帰呼び出しはありません。

`count` は走査N回、逆順伝播V回、結果の取得P回で $O(N+V+P)$ です。
`count_matches` は $O(N+1)$、全列挙は一致数Kに対して $O(N+K+1)$ です。

## 改造時の注意点

`child` にfailure経由の遷移を書き込むと、構築後の追加登録が実際の辺と区別できなくなります。
この2つの表を統合する場合は、登録を構築前だけに限定するなど、APIの前提も変えてください。
文字は `unsigned char` として扱い、全256バイト値や埋め込みの0も受け付けます。

DPでは `next` と `match_count` を使い、禁止パターンに一致した状態への遷移を除外できます。
空パターンがある場合は初期状態でも一致する点に注意してください。
ノードの削除は実装していません。削除対応では終端ID・一致数・各リンクの整合性を考慮する必要があります。

## 改造後の確認

`he, she, his, hers`、接尾辞の入れ子、同一パターンの重複、空パターン・空テキスト・登録なしを確認します。
各パターンと各開始位置を直接比較する愚直解と、回数・一致位置・各状態の一致IDを照合します。
再構築と追加登録後も同じ比較を行い、既存の終端番号が変わらないことを確認します。
長い一本道では再帰に依存しないこと、多数の接尾辞一致では回数集計が全列挙に依存しないことを確認します。
